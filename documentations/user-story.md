## User Stories

#### 1. Запуск исследования
> *«Я открываю страницу в браузере и хочу сразу начать работу, не дожидаясь загрузки данных.»*
-   Пользователь заходит на `localhost:5173` (dev-сервер Vite; backend — `localhost:8000`).
-   Видит индикатор статуса системы (зеленый/красный) на основе `GET /health`. Если всё ок — интерфейс разблокирован.
-   Текущие значения параметров уже подставлены в слайдеры: при старте frontend выполняет `GET /api/model` и использует поле `current_configuration` (буфер `data/model.json`, который система заполняет из `comparison.json` при первом запуске бэкенда).

#### 2. Настройка параметров сжатия («Покрутить ручки»)
> *«Я хочу изменить параметры модели и увидеть, как это повлияет на результат, прямо на экране, без лишних кликов.»*
-   Пользователь двигает ползунки `param_a`, `param_b`, `param_c` (список и диапазоны приходят из `GET /api/model`, min/max слайдера — поле `ui_range`; ничего не зашито во фронтенде).
-   Интерфейс реагирует **мгновенно** (через debounce ~200ms): метрики и графики пересчитываются автоматически при каждом движении — frontend отправляет `POST /api/predict` со **всеми** параметрами сразу (backend отклоняет неполную конфигурацию ошибкой 422).
-   Кнопка «Применить» отсутствует; пользователь видит изменение результатов в реальном времени.
-   Пользователь видит текущие значения параметров рядом с элементами управления.

#### 3. Сравнение моделей («Полная vs Урезанная»)
> *«Я хочу визуально оценить, насколько "урезанная" модель отличается от оригинальной.»*
-   На экране отображаются две метрики или графика рядом: «Original Accuracy» и «Compressed Accuracy». Значения берутся из массива `metrics` ответа `GET /api/model`: поля `full` (полная модель) и `compressed` (сжатая модель) для каждой метрики.
-   Пользователь видит разницу (delta) в процентах или абсолютных значениях — backend уже возвращает готовые `absolute_delta` и `relative_delta`, повторно вычислять их не нужно.
-   Есть визуальная индикация качества (цвет меняется с зеленого на желтый/красный при сильной деградации относительно baseline compressed-метрики).

#### 4. Анализ чувствительности («Что важнее?»)
> *«Я хочу понять, какой параметр сильнее всего влияет на качество модели, чтобы не трогать его лишний раз.»*
-   В интерфейсе присутствует интегрированный блок (не отдельная вкладка) с ранжированием параметров по влиянию на ошибку. Источник данных — поле `sensitivity` каждого параметра из `GET /api/model` (frontend только сортирует и показывает, сам ничего не пересчитывает).
-   Пользователь видит список параметров, отсортированный по значимости.
-   Может кликнуть на параметр в списке, чтобы подсветить соответствующий ползунок или увидеть детальную информацию о его влиянии.

#### 5. Просмотр истории экспериментов
> *«Я менял параметры 10 раз и хочу вернуться к тому удачному варианту, который был 5 минут назад.»*
-   В интерфейсе есть список сохраненных прогонов (`exp_001`, ...), загружаемый через `GET /api/experiments` (источник на backend — папка `data/experiments/`).
-   Пользователь кликает на запись в списке — все ползунки автоматически устанавливаются в значения конфигурации этого эксперимента (поле `configuration` записи).
-   Метрики и графики мгновенно обновляются под выбранную конфигурацию (выполняется `POST /api/predict` для этой точки).
-   Видит дату (поле `timestamp`, ISO-формат; у части записей дата может отсутствовать — тогда отображается заглушка) и ключевые метрики каждого сохраненного запуска (поле `metrics` записи — словарь `имя метрики -> измеренное compressed-значение`).

#### 6. Сброс к исходному состоянию («Вернуться к якорю»)
> *«Я запутался в настройках и хочу гарантированно вернуться к проверенной базовой точке отсчета.»*
-   Кнопка «Reset to baseline» вызывает `POST /api/reset`: backend сбрасывает буфер `data/model.json` строго к значениям из файла `comparison.json` (источник истины) и возвращает prediction базовой конфигурации.
-   После сброса frontend устанавливает ползунки в `configuration` из ответа reset; предсказанные метрики точно совпадают с эталонными метриками сжатой модели (field `baseline` в ответе).
-   Это гарантирует возврат к «якорю», даже если текущий буфер `model.json` был изменен или поврежден.

#### 7. Мониторинг в реальном времени
> *«Я хочу видеть накопленную историю своих действий и сравнение с реальными данными.»*
-   Пользователь видит встроенный через iframe Grafana Dashboard (URL из `VITE_GRAFANA_DASHBOARD_URL`).
-   На дашборде отображаются как реальные данные black-box (actual), так и результаты его интерактивных манипуляций (predicted).
-   История изменений накапливается в InfluxDB автоматически при каждом успешном `POST /api/predict` (то есть практически при каждом движении ползунка после debounce); frontend не должен ждать обновления Grafana, чтобы показать prediction.

---

### Чего пользователь НЕ делает (через UI):
-   Не пишет JSON-конфиги вручную.
-   Не выбирает файлы для загрузки (система сама берет `model.json` / `comparison.json`).
-   Не нажимает кнопку «Применить» после изменения параметров (всё происходит реактивно).
-   Не рестартит сервер (это делает админ/devops).
-   Не смотрит логи консоли (все ошибки выводятся в UI-уведомлениях/toasts; текст ошибки берется из поля `detail` ответов 422).
-   Не работает напрямую с InfluxDB или Grafana API (только через iframe и backend).
